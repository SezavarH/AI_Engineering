1. REST, HTTP and API design

Before you start, you must know:
  • Python function: a named block that accepts input and returns output.
  • JSON: text representing objects, arrays, strings, numbers, booleans and null.
  • Network request: a client sends bytes to a server and waits for a response.
Resource→URI→HTTP method→ Request→Server→Status→Representation
📖 How to read this mind map: Resource is the thing the API manages. URI names where it lives. The HTTP method says what operation the caller wants. The server processes it. Status communicates the outcome. Representation is the data sent back.
What is a resource?

What is it? A resource is a thing your API exposes, such as a product price.

Why does it exist? Clients need a stable concept to address instead of calling arbitrary server functions.

When? Use a resource when clients need to read or manipulate identifiable application data.

Where? Its URI is designed in the API layer, for example /prices/A1.

GET /prices/A1
→ {"sku":"A1","price":19.90}

What breaks if skipped? Your API becomes a collection of ad-hoc commands whose semantics are difficult to predict.

What is a URI?

What is it? A URI is the identifier a client uses to refer to a resource.

Why? It separates “what thing?” from “what operation?”

When? Use a stable URI for resources and collections.

Where? In route declarations such as /prices/{sku}.

/prices
/prices/A1

Failure mode: putting verbs into every path, such as /getPrice, makes HTTP semantics harder to compose.

What does stateless mean?

What is it? Each request contains the information needed to understand it rather than depending on hidden server-side conversation state.

Why? Any healthy server instance can handle the next request.

When? It is the default REST design principle; authentication tokens are normally sent with each request.

Where? Request headers, path, query and body.

GET /prices/A1
Authorization: Bearer TOKEN

Failure mode: a client works only when routed back to worker #2 because worker #2 remembers an undocumented session state.

💡 Why REST exists: REST gives clients a uniform interface around resources over HTTP. It favors cacheability, stateless interactions and predictable semantics.

Takeaway: HTTP semantics are part of your API contract, not decoration.

Pydantic: turning untrusted data into typed application data

Before you start, you must know:
  • Resource — the API-managed thing.
  • HTTP request/body — data supplied by the caller.
  • Response representation — data returned to the caller.
What is BaseModel?

What is it? BaseModel is a Python class whose instances validate, parse and serialize structured data.

Why? Raw dictionaries do not enforce types or constraints.

When? Use it at data boundaries and for explicit schemas.

Where? Usually app/models/ or feature-local schemas.py.

from pydantic import BaseModel
class PriceRequest(BaseModel):
    sku: str
    amount: float

Failure mode: invalid data leaks into services and errors appear far away from the actual boundary.

Named-type mapping

Same scenario, three types

# Request: what client may send
class PriceRequest(BaseModel):
    sku: str = Field(min_length=6, max_length=6)
    amount: float = Field(gt=0)

# Internal: what business logic needs
@dataclass
class Price:
    id: str
    sku: str
    amount_cents: int
    supplier_id: str

# Response: what client is allowed to see
class PriceResponse(BaseModel):
    id: str
    sku: str
    amount: float

The request contains user-facing units. The internal model uses integer cents and a private supplier ID. The response deliberately excludes internal data.

Field constraints

What is it? A Field declares constraints and metadata for one field.

Why? Validation should be executable rather than living only in documentation.

When? Use built-in constraints for simple rules.

Where? Request/response schema definitions.

sku: str = Field(min_length=6, max_length=6)
qty: int = Field(gt=0)

Failure mode: invalid values reach business logic.

Validators

What is it? A validator is a function that enforces a rule more complex than a simple type/constraint.

Why? Some rules involve normalization or multiple fields.

When? Use it when the rule belongs to the schema boundary.

Where? The Pydantic model.

from pydantic import field_validator

class SKU(BaseModel):
    value: str

    @field_validator("value")
    @classmethod
    def uppercase(cls, v):
        return v.upper()

Failure mode: every caller implements normalization differently.

Serialization and validation 
payload = request.model_dump()
obj = PriceResponse.model_validate(payload)

model_dump() produces Python data. model_validate() constructs a model from compatible data.

⚠️ Junior trap: returning your ORM/domain object directly can accidentally expose internal fields.
🎯 Senior habit: external schema and internal domain model may look similar, but they have different ownership and change rates.
Takeaway: Pydantic turns API boundaries into executable contracts.
You can now do: distinguish request, domain and response types.

FastAPI core constructs

Before you start, you must know:
  • HTTP verbs and status codes.
  • Pydantic models.
  • Request/response boundary.

Path, query and body parameters

What is it? Three places where request input can live.

Why? The location communicates semantics.

When? Path identifies a resource; query modifies/filter the read; body carries structured content.

Where? Route function signature.

@app.get("/prices/{sku}")
async def get_price(
    sku: str,                 # path
    region: str = "EU",       # query
):
    ...

@app.post("/prices")
async def create_price(req: PriceRequest):  # body
    ...

Failure mode: clients cannot predict where inputs belong.

Routers

What is it? APIRouter groups related routes.

Why? A single application file becomes unmaintainable.

When? Feature boundaries or API versions.

Where? app/routers/price.py.

router = APIRouter(prefix="/v1/prices")

@router.get("/{sku}")
async def get_price(sku: str):
    ...

Failure mode: routes, dependencies and unrelated business logic become one giant module.

Middleware

What is it? Middleware wraps requests before and after route handling.

Why? Cross-cutting behavior should not be copied into every route.

When? Request IDs, timing, trusted proxy handling, broad headers.

Where? app/main.py.

@app.middleware("http")
async def timing(request, call_next):
    start = time.monotonic()
    response = await call_next(request)
    response.headers["X-Time"] = str(time.monotonic()-start)
    return response

Failure mode: duplicated instrumentation and inconsistent behavior.

Exception handler

What is it? A function that converts a raised exception into a controlled HTTP response.

Why? Raw exceptions otherwise become generic 500 responses.

When? For consistent public error shapes.

Where? API/application setup.

@app.exception_handler(ValueError)
async def handle_value_error(request, exc):
    return JSONResponse(
        status_code=400,
        content={"error":"bad_request"}
    )

Failure mode: clients receive inconsistent errors and sensitive stack traces may leak.

BackgroundTasks

What is it? FastAPI's small mechanism for work scheduled after the response is sent.

Why? Some lightweight work does not belong on the critical response path.

When? Small non-critical tasks such as writing a local audit event.

Where? Route layer.

from fastapi import BackgroundTasks

@app.post("/price")
async def price(background_tasks: BackgroundTasks):
    background_tasks.add_task(write_audit)
    return {"ok": True}

Failure mode: using it for durable jobs means work can disappear when the process dies.

⚠️ For durable jobs use a real queue/worker system rather than treating BackgroundTasks as a distributed job queue.
Takeaway: FastAPI constructs solve different boundaries; do not use middleware, dependencies and background tasks interchangeably.
You can now do: organize an API into routes, schemas, cross-cutting middleware and controlled errors.

Depends — the dependency graph

Before you start, you must know:
  • Route functions — receive request inputs and return responses.
  • Typed schemas — define structured boundaries.
  • Request lifecycle — server receives request, executes code, returns response.
💡 Plain English: Depends means: “Before the route runs, call this function and hand me its return value.”

Why was it invented? Without dependency injection, routes manually create auth objects, DB sessions, clients and configuration.

# Naive
async def route():
    db = make_db()
    user = get_user()
    return await service(db, user)
# Dependency
async def route(
    db=Depends(get_db),
    user=Depends(get_user)
):
    return await service(db, user)

How it works under the hood: FastAPI inspects the route signature and resolves dependencies before calling the route. It builds a dependency graph, resolves sub-dependencies, and by default caches each dependency result for that request (use_cache=True).

Example A — constant configuration

def get_region():
    return "EU"

@app.get("/prices")
async def prices(region=Depends(get_region)):
    return {"region": region}

Use this when: a value has one injection point and you want easy replacement in tests.

Example B — DB/session-like resource

async def get_db():
    db = await pool.acquire()
    try:
        yield db
    finally:
        await pool.release(db)

@app.get("/prices/{sku}")
async def price(sku: str, db=Depends(get_db)):
    return await db.fetch_price(sku)

Why yield? Code before yield prepares the resource; code after it cleans it up after the request.

Example C — current user from a header

async def current_user(
    authorization: str = Header(...)
):
    token = authorization.removeprefix("Bearer ")
    return await verify_token(token)

@app.get("/me")
async def me(user=Depends(current_user)):
    return {"user_id": user.id}

Example D — yield resource with cleanup

async def get_http_client():
    client = httpx.AsyncClient(timeout=5)
    try:
        yield client
    finally:
        await client.aclose()

Class-based dependency with __call__

class Region:
    def __init__(self, default):
        self.default = default

    def __call__(self, x: str | None = None):
        return x or self.default

eu_region = Region("EU")
region = Depends(eu_region)

Overriding in tests

app.dependency_overrides[get_db] = fake_db
response = await client.get("/prices/A1")
assert response.status_code == 200
app.dependency_overrides.clear()
⚠️ Common misuses: performing I/O at import time; using an async dependency when it does no async work; forgetting yield cleanup for leased resources.
🎯 Senior habit: Dependencies are boundaries for replaceable infrastructure. Keep business rules in services, not inside dependency plumbing.
Takeaway: Depends builds a per-request dependency graph and gives you clean lifecycle/test seams.
You can now do: inject DB, auth and clients without constructing them inside every route.

Advanced · v4 — errors + lifespan, separated first

What is an exception handler?

It is the application's translator from an exception into a controlled HTTP response.

@app.exception_handler(PricingUnavailable)
async def pricing_error(request, exc):
    return JSONResponse(
        status_code=503,
        content={"error":"pricing_unavailable"}
    )

Line 1 registers the handler. Line 2 receives the request and exception. The response communicates a temporary dependency failure rather than pretending the client made a bad request.

What is lifespan?

Lifespan is the app's opening and closing ceremony: code before yield runs once at startup; code after it runs once at shutdown.

@asynccontextmanager
async def lifespan(app):
    app.state.pricing = PricingClient(timeout=5)
    yield
    await app.state.pricing.close()

app = FastAPI(lifespan=lifespan)

The client is created once. Shutdown closes it exactly where its lifecycle is defined.

Takeaway: resources live across the application lifetime; exceptions are translated at the HTTP boundary.

Senior · v5 — production-shaped final 
class PriceResponse(BaseModel):
    sku: str
    total: float
    request_id: str

@app.get("/health")
async def health():
    return {"status": "ok"}

@router.post(
    "/price",
    response_model=PriceResponse
)
async def price(
    body: PriceRequest,
    client=Depends(get_pricing_client),
    request_id: str = Depends(get_request_id),
):
    try:
        async with asyncio.timeout(5):
            unit = await client.get(body.sku)
    except TimeoutError:
        raise PricingUnavailable()

    return PriceResponse(
        sku=body.sku,
        total=unit * body.qty,
        request_id=request_id,
    )
  • Notice: response contract, timeout, health endpoint, request-scoped ID.
  • Scale failure if skipped: downstream hangs consume capacity; debugging becomes correlation-free; accidental response fields become public API.

Where this lives: app/routers/price.py.

🎯 Senior interview question: “Why not create the HTTP client inside the route?” Answer: because connection pools should be reused, lifecycle should be explicit, and tests need a replaceable dependency.
Q1. A downstream call hangs for 90 seconds. Which design property matters first?
A. A timeout turns unbounded waiting into a bounded resource cost and allows capacity to recover.
Q2. Why is 422 appropriate for invalid qty=-1?
A. The request reaches the HTTP endpoint but violates its declared input constraints.
Q3. Why separate response models from internal objects?
A. Public contracts should expose only fields the client is entitled to receive.
Takeaway: A production FastAPI endpoint is a contract + lifecycle + dependency + timeout + error boundary.

2. Async & concurrency in Python

Before you start, you must know:
  • FastAPI route — server code called for one request.
  • HTTP client dependency — network I/O may take time.
  • Request lifecycle — many clients can be active at once.
Coroutine→await→event loop→task→concurrency limit
📖 How to read this mind map: A coroutine describes async work. await gives control back while waiting. The event loop schedules other work. A task schedules a coroutine. A concurrency limit prevents too much simultaneous work.

The four execution models

GIL in one sentence

The CPython Global Interpreter Lock generally prevents multiple threads from executing Python bytecode simultaneously in one interpreter.

It does not mean threads cannot overlap I/O, and it does not mean processes cannot execute Python CPU work in parallel.

Same scenario: fetch 10 URLs

Caller: internal price aggregator.

Input: ten supplier URLs.

Goal: collect all responses.

Rule: each request has a 2-second timeout; at most five suppliers should be contacted simultaneously.

# sync
def fetch_all(urls):
    return [requests.get(u, timeout=2).json() for u in urls]
# async
async def fetch_all(urls):
    return await asyncio.gather(
        *(fetch(u) for u in urls)
    )
# threads for blocking SDK
with ThreadPoolExecutor(max_workers=5) as pool:
    results = list(pool.map(fetch_sync, urls))
# processes for CPU-heavy transformation
with ProcessPoolExecutor() as pool:
    results = list(pool.map(cpu_transform, payloads))
Illustrative wall-clock timeline: sequential work waits end-to-start; concurrency overlaps independent work.

Decision tree

📖 How to read it: First classify the bottleneck. Network waits favor async; blocking libraries favor a thread bridge; CPU-heavy Python favors processes; any expensive boundary needs a capacity limit.

Async primitives — one at a time

await — wait without blocking the event loop

What: pauses the current coroutine until another awaitable completes.

Why: the loop can run other tasks while this one waits.

How: the coroutine suspends at the await point; the event loop schedules something else.

async def price():
    data = await client.get("/price")
    return data

Scenario: API calls supplier pricing. Use when: the operation is awaitable. Misuse: calling blocking requests.get() inside async code.

asyncio.create_task — start now, keep a handle
async def save_audit():
    await audit.write()

task = asyncio.create_task(save_audit())
result = await do_main_work()
await task

What: schedules a coroutine immediately and returns a Task.

Why: overlap independent work while retaining cancellation/result control.

Misuse: fire-and-forget without ownership. If the process dies, the work is lost.

asyncio.gather — all results
results = await asyncio.gather(
    fetch("A"),
    fetch("B"),
    fetch("C"),
)

What: schedules awaitables concurrently and returns results in input order.

Use: independent operations where all results are required.

Mistake: passing 100,000 tasks without a limit.

gather(..., return_exceptions=True)
results = await asyncio.gather(
    fetch("A"), fetch("B"),
    return_exceptions=True,
)
for result in results:
    if isinstance(result, Exception):
        log_failure(result)

What: returns exceptions as values instead of failing the whole gather.

Use: tolerant batch operations.

Mistake: forgetting to inspect returned exceptions.

asyncio.as_completed — consume fastest first
tasks = [fetch(u) for u in urls]
for task in asyncio.as_completed(tasks):
    result = await task
    yield result

What: yields awaitables in completion order.

Use: UI/progressive aggregation where fast results are valuable immediately.

asyncio.wait_for — deadline
try:
    result = await asyncio.wait_for(
        fetch(url), timeout=2
    )
except asyncio.TimeoutError:
    return fallback

What: stops waiting after a specified duration.

Use: dependency deadlines.

asyncio.TaskGroup — structured concurrency
async with asyncio.TaskGroup() as tg:
    a = tg.create_task(fetch("A"))
    b = tg.create_task(fetch("B"))

print(a.result(), b.result())

What: owns a group of tasks and coordinates their lifetime.

Why: if one task fails, the group can cancel siblings and propagate failure together.

Use: related concurrent operations where task lifetime must be structured.

asyncio.Semaphore — cap concurrency
sem = asyncio.Semaphore(5)

async def fetch(url):
    async with sem:
        return await client.get(url)

What: permits only N coroutines into a critical region at once.

Use: protect supplier APIs, DB pools and model endpoints.

anyio.to_thread.run_sync — bridge blocking code
import anyio

result = await anyio.to_thread.run_sync(
    legacy_sdk.generate,
    prompt,
)

What: runs synchronous work in a worker thread.

Use: a third-party SDK has no async API.

Mistake: creating unlimited thread work.

v5 — structured production version
async def fetch_all(urls):
    sem = asyncio.Semaphore(5)

    async def one(url):
        async with sem:
            try:
                async with asyncio.timeout(2):
                    return await fetch(url)
            except TimeoutError:
                return SupplierTimeout(url)

    async with asyncio.TaskGroup() as tg:
        tasks = [tg.create_task(one(u)) for u in urls]

    return [task.result() for task in tasks]
  • Notice: bounded work, deadline, owned task lifetime.
  • Scale failure: without these, downstream overload and stuck requests amplify each other.

Where: app/services/suppliers.py.

Q1. Ten HTTP calls take 1 second each. Why can async finish near 1 second instead of 10?
A. While one request waits for network bytes, the event loop can progress another request.
Q2. Why cap 1000 outbound calls to five?
A. Concurrency is a resource budget, not a goal in itself.
Q3. A sync SDK is used in an async route. What is the main danger?
A. The blocking SDK occupies the event-loop thread and delays unrelated requests.
Takeaway: Async is about overlapping waits; senior concurrency adds deadlines, cancellation and bounded capacity.

3. Server-Sent Events

Before you start, you must know:
  • HTTP request/response.
  • async/await — waiting without blocking the event loop.
  • bounded concurrency — limiting expensive work.

What is a stream?

A normal response is like ordering a complete book. A stream is like a radio broadcast: pieces arrive while the source is still producing them.

What is SSE?

What: SSE is a long-lived HTTP response in which the server sends text events to a browser as they become available.

Why: a normal HTTP response waits for the complete body.

When: LLM tokens, progress updates, notifications, live logs.

Where: a streaming route such as app/routers/stream.py.

data: hello

data: world

Failure mode: users wait for a 20-second AI response instead of seeing the first token quickly.

SSE wire format

Each event is UTF-8 text. Fields end with a newline. A blank line terminates an event.

event: token\n
id: 41\n
retry: 3000\n
data: {"token":"Hel"}\n
\n
event: token\n
id: 42\n
data: {"token":"lo"}\n
\n
event: done\n
id: 43\n
data: {}\n
\n
  • event: names the event type.
  • data: contains the payload.
  • id: identifies the event for resume.
  • retry: suggests reconnect delay.
  • blank line means “this event is complete”.

v5 — production-shaped LLM stream
async def generate_stream(request, llm, last_id=None):
    queue = asyncio.Queue(maxsize=100)

    async def producer():
        async for token in llm.stream():
            await queue.put(token)

    producer_task = asyncio.create_task(producer())

    try:
        while True:
            if await request.is_disconnected():
                producer_task.cancel()
                break

            try:
                token = await asyncio.wait_for(
                    queue.get(), timeout=15
                )
                yield {
                    "id": token.id,
                    "event": "token",
                    "data": token.text,
                }
            except TimeoutError:
                yield {"comment":"heartbeat"}
    finally:
        producer_task.cancel()
        logger.info("sse_closed", extra={"last_id":last_id})
  • Notice: bounded queue, cancellation, heartbeat, IDs, structured logging.
  • Scale failure: unbounded buffering consumes memory; ignored disconnects waste model tokens; missing IDs prevent reliable resume.

Production checklist

Proxy: disable buffering.
Timeouts: account for long-lived connections.
Auth: EventSource header limitations need cookie/session or fetch-stream strategies.
CORS: configure explicit allowed origins.
Rate limits: streaming connections consume capacity for longer.
Fan-out: Redis Pub/Sub can distribute transient events.
Resume: retain event IDs long enough to replay.
Backpressure: bound queues.

What is Redis?

What: Redis is a server that keeps data primarily in memory and exposes fast operations over a network protocol.

Why: an application process cannot safely share one Python dictionary across multiple workers or machines.

When: shared cache, ephemeral state, counters, locks, queues or event streams.

Where: infrastructure layer, accessed by services.

Failure mode: treating Redis as “just a dictionary” can cause data loss assumptions, memory exhaustion or stale data.

Dockerfile→Build context→Layers→ Image→Container→Process
📖 How to read this map: Dockerfile describes construction. Build context is the files available to the builder. Each instruction can create a layer. The image is the packaged result. A container is one runtime instance of that image. The process is the actual application program.
What is an image?

What: an image is an immutable packaged filesystem and metadata used to start containers.

Why: “install Python, install dependencies, copy app” should be reproducible.

When: build once, run in many environments.

Where: Dockerfile and registry.

Failure mode: machines drift because each developer installs dependencies differently.

What is a container?

What: a container is a running process isolated using Linux kernel features and configured from an image.

Why: isolate filesystem, process and network assumptions.

When: run the application consistently.

Where: local development, CI, deployment.

Failure mode: without isolation, runtime assumptions leak between applications.

Senior interview: architecture walkthrough

📌 Question: “Design this for 500 concurrent streaming users.”
  • Start with request validation and authentication.
  • Give every upstream dependency a timeout.
  • Use async clients for network I/O.
  • Bound concurrent LLM requests with a semaphore or provider capacity.
  • Use bounded queues for token buffering.
  • Detect client disconnects and cancel upstream generation.
  • Cache only data whose freshness policy is explicit.
  • Instrument cache hit ratio, upstream latency, time-to-first-token, active streams and error rate.
  • Keep Redis failure separate from source-of-truth failure.
  • Build immutable images and promote the exact tested artifact.

Scenario 2 — graceful model cancellation

async def stream(request):
    task = asyncio.create_task(
        llm.stream()
    )
    try:
        while True:
            if await request.is_disconnected():
                task.cancel()
                break

            token = await task
            yield token
            task = asyncio.create_task(
                llm.next_token()
            )
    finally:
        task.cancel()
  • Notice: connection lifetime owns model work.
  • Scale failure: disconnected browsers can continue consuming model capacity.

Scenario 3 — production health separation

@app.get("/health/live")
async def liveness():
    return {"status":"alive"}

@app.get("/health/ready")
async def readiness():
    if not app.state.redis_ready:
        raise HTTPException(503, "not_ready")
    return {"status":"ready"}
  • Notice: liveness asks “is the process alive?” readiness asks “should traffic be sent here?”
  • Scale failure: one overloaded/unready instance may keep receiving traffic.

Final senior decision drills

Q1. Redis is down, but the upstream pricing API works. What should happen?
B. If Redis is not the source of truth, its outage should not automatically become a pricing outage. The fallback must still respect upstream capacity.
Q2. An SSE client disconnects after receiving 20 tokens. What should happen to the model request?
B. Client disconnect is a capacity signal. Continuing expensive generation wastes compute and provider quota.
Q3. Tests pass, but Docker build fails. Should production deploy?
A. The deployable artifact does not exist. CI should make artifact creation part of the gate before promotion.
